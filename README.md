# Hospitality OS

Cloud hospitality operating system (PMS core; CRS, booking engine, channel manager, portals and apps to follow).
Architecture and product decisions: [`docs/phase-0/00-index.md`](docs/phase-0/00-index.md). Pilot: Sunset BnB (Boulevard, Creek, Ramna).

## Status — Phase 1, milestone M0 (foundations)
**Slice 1:** monorepo; `@hos/db` (SQL migrations, forced RLS on every tenant table, `withTenant()`); tenant-isolation suite (schema lint + RLS tests, CI gate); `@hos/domain-types` `Money`; API skeleton.
**Slice 2 (this):**
- `@hos/auth`: pure authorization engine — scoped grants (tenant / legal entity / property / department), validity windows, limits (discount, refund, adjustment) that yield *approval required*, and **privilege-escalation guards** for role assignment; system role templates
- API: global permission guard (**deny by default**; every route must declare a permission or be explicitly `@Public`, enforced by a contract test), tenant middleware + correlation ids, RFC 9457 problem+json errors, 404-not-403 for foreign resources
- Audit service (same-transaction, redacting), **transactional outbox** + relay (ordered per aggregate, retry, dead-letter, safe with concurrent relays), idempotent inbox, **idempotency keys** (exactly-once under concurrency)
- Tenant provisioning (roles seeded per tenant, owner, audit + `TenantCreated` event)
**Slice 3 (identity):** invitation → password (Argon2id, length-first policy), login with lockout and non-enumerating errors, server-side sessions (hashed opaque tokens in `__Host-` cookies, idle + absolute expiry), CSRF token + Origin allow-list, TOTP two-factor (RFC 6238, encrypted seeds, replay protection, recovery codes), **step-up MFA for sensitive permissions**, password change with session revocation, staff language preference (English / Urdu), audit-log read endpoint.
**Slice 4 (property setup + availability):** property wizard backend (properties, buildings/floors, room types, rooms with bulk generator and connecting rooms, tenant amenity catalogue, setup status, go-live), the **availability engine** (per room-type/night counters mutated only by conditional atomic updates with date-ordered locking; physical-room assignment and block overlap prevented by database exclusion constraints; overbooking limits per date; out-of-order/out-of-service blocks with oversell protection and explicit acknowledgement; invariant checker), optimistic locking, business dates as plain calendar dates in the property's time zone, audit + `InventoryChanged` events.
**Slice 5 (rate engine):** `@hos/rates` pure pricing engine (override > season > weekend/weekday; derived plans for local/international and corporate; extra adult/child/bed/meal; restrictions; deposit; 72-hour cancellation and no-show fees from a policy snapshot), rate plans/seasons/overrides/restrictions API with dry-run and >30% guard rail, rate calendar, quote search with signed 15-minute tokens.
**Slice 6 (reservations, placeholder prices):** guests (phone normalisation, duplicate warning), reservations as header + room lines + per-night price snapshot + immutable history; create with idempotency keys and server-side re-pricing of signed quotes (client never sets the price); OPTION holds with expiry, confirm / cancel / no-show / reinstate / reconfirm through one state machine; 72-hour cancellation and no-show fees measured to the property's check-in time, waiver needs permission + fresh MFA; modify (extend, shorten, upgrade, occupancy, keep-rate); room assignment; at-risk flag and guarantee deadline for unguaranteed OTA bookings (PayFast hook point); concurrency-tested (12 racers for 3 rooms → exactly 3 succeed).
**Slice 7 (room rack + front desk):** the room rack (tape chart) API — every room with its stays, blocks, housekeeping state, unassigned bookings, per-type availability and today's arrivals/departures/in-house/no-show/at-risk counts; check-in with registration card (CNIC / NICOP / passport validated and **encrypted at rest**, masked unless the user has the view-ID permission and a fresh second factor), local guests on local rates and foreign guests on passports; room-readiness rules (dirty, occupied, blocked rooms need an audited override); same-day undo; check-out with early-departure (cuts the stay and bill, frees the nights for sale) and overstay flags; in-house room moves with history; walk-ins (price → book → check in atomically, idempotent, auto-picks a clean room); minimal housekeeping status (dirty on check-out) that the housekeeping module will build on. The folio balance gate on check-out arrives with the folio slice.
**Slice 8 (folio, payments, cashier):** an immutable posting ledger (append-only in the database; the folio balance moves with every posting inside the database, closed business dates cannot be posted to); one guest folio per reservation, opened at check-in or first deposit; room nights posted idempotently (one charge per night per code); manual charges, limit-checked discounts, corrections by reversal only; payments by cash (needs your open cashier session), card slip, wallet and bank transfer (a second person verifies; nobody verifies their own entry); idempotent money requests; deposits that secure unguaranteed bookings (and un-secure them when voided or refunded); refunds capped at what was paid, non-cash refunds approved by a second person; cancellation / no-show fees posted as charges (a held deposit offsets them) and taken back on reinstatement; blind cashier close with variance review by a different manager; check-out refuses a balance (or overpayment) unless a manager with the right permission and a fresh second factor overrides it with a reason, and closes the folio when it is settled; ledger invariant checker. **Tax and invoices are the next slice** — amounts are ex-tax until the tax engine (waiting on the advisor's worksheets) adds TAX postings.
**Slice 9 (housekeeping + staff app):** housekeeping tasks (check-out clean queued the moment a room is vacated — urgent if a guest arrives into it today, most urgent for a VIP; stay-over, arrival-prep and back-from-out-of-order deep cleans generated daily and repeatably), supervisor assignment, the attendant flow (start → cleaning → finished, one room at a time, put back, guest declined, do-not-disturb), optional inspection with rework, board with workload and averages, room problems reported by staff, lost & found. Rooms being cleaned or dirty are not ready for a guest. **`apps/staff-web`**: a mobile-first installable web app in English and Urdu (right-to-left) that keeps working with no signal (offline queue with true timestamps, idempotent replays) — see `apps/staff-web/README.md`. Housekeeping demo team: `pnpm --filter @hos/api seed:demo-staff`.
**Slice 10 (night audit):** the business date only moves through a night audit. Pre-checks (open cashier sessions can never be skipped; overdue departures, an audit run before the day is over, ledger or availability inconsistencies need a manager's override with a reason, a fresh second factor and are recorded; pending arrivals and unverified transfers are warnings). Steps run in order and are resumable: no-shows (with their fee), expire unpaid holds, post the night's room charges, taxes (reserved place — arrives with the tax engine), then one closing transaction that freezes postings, catches stragglers, writes an **immutable daily snapshot** (occupancy, room revenue, ADR, RevPAR, movement, payments by tender, guest ledger, deposits held, cashier variance, the day's lists), rolls the date with compare-and-set, extends the inventory horizon and generates tomorrow's housekeeping. A failed step stops the run cleanly and the next start resumes at that step; two simultaneous starts close the day once; a stalled run is picked up. A posting can never slip into a closed day (database-level freeze). Reports: `GET /v1/properties/:id/night-audit/reports[/:date]`.
**Slice 11 (front-office screens):** the staff app now covers the desk. **Today** (arrivals / in house / departures with counts, warnings and search), **Rack** (tape chart: rooms × 14 days, bars for stays, unassigned bookings, tap a free night to book), **Bookings** (search by name / phone / booking no. / OTA reference; new booking: availability → price with the cancellation policy in plain words → guest (duplicate warning, local/foreign rate match) → confirm or hold; walk-in in one step), the **reservation sheet** (stay, bill, history; assign / move room, cancel, no-show, WhatsApp click-to-chat), **check-in** (room readiness, registration card with ID numbers), **check-out** (settle the bill, early departure, manager override), **payments and charges**, **cashier** (blind close, drops, bank-transfer verification, variance review) and **night audit** (what is in the way, manager overrides, run, day reports). Desk layout on wide screens, phone layout on small ones; English and Urdu throughout; sensitive actions ask for the second-factor code on the spot. Built-in roles are brought up to date for existing tenants with `pnpm --filter @hos/api roles:sync`; `scripts/reset-dev.sh` rebuilds the local dev database with the demo data.
Not yet: reservations, rack, front desk, folio, payments, tax engine, night audit, observability, Terraform (AWS comes after everything runs locally), i18n scaffolding.

**Slice 12 (tax engine and invoices):** the product ships with **no tax rates**. The owner or accountant enters a tax (code, jurisdiction) and its rate versions (basis points, dates, residency, which charge types); a version is a draft until a *different* person approves it with the tax advisor's reference and legal basis, and only one approved rate can cover a code on any date. Each property is pointed at a jurisdiction. Tax is added beside each charge as it is posted (exclusive pricing, half-away-from-zero rounding, rate and taxable value recorded; reversing a charge reverses its tax; quotes show tax and the total with tax); the night audit catches up anything posted before a rate existed and reports tax apart from revenue, and a liability report agrees with the ledger. After check-out, **invoices** are issued from the bill: immutable, gapless numbers per legal entity, series and financial year (July–June or any start month), tax by line and by code, optional bill-to company with NTN/STRN, a print view, and a content hash. A **credit note** reverses a whole invoice (manager + second factor + reason); the items can then be invoiced again. Not yet built: exemption certificates, rates that depend on how the guest pays, tax-inclusive pricing, component allocation (package splits) and the GL mapping. Migration `0012`; run `pnpm --filter @hos/api roles:sync` after pulling.

**Slice 13 (corporate accounts and receivables):** **Companies** are tenant-wide accounts with registered numbers (NTN/STRN), a credit limit (0 = no credit), payment terms (net days) and a status (active / on hold / archived). Changing the limit or terms asks for the second-factor code. A quote can only name a company that exists and is not archived. At the desk, **Bill to company** moves part or all of a guest's balance off their bill (a ledger posting) onto the company's account, due after its terms; it stops at the credit limit or when the company is on hold, and a manager can override with a reason and the second factor. A billing can be cancelled while nothing has been paid against it. **Payments received** (bank transfer, cheque, wallet) are recorded by one person and verified by another; they settle the oldest unpaid bills first (or the ones named), tax the company withheld also settles what it owes (with its certificate number), and surplus stays as credit on account and is used by the next billing. A company's **statement** (printable) shows billed and received with a running balance and **ageing** (not yet due / 1–30 / 31–60 / 61–90 / 90+). Invoices can be made out to the corporate account with its registered numbers and show the amount as charged to the account. Migration `0013`; run `pnpm --filter @hos/api roles:sync` after pulling. Not yet built: write-offs, credit notes against a company's account, per-company statements by e-mail/WhatsApp, and the GL mapping.

**Slice 14 (management overview):** a read-only **Management** tab for owners and managers (`management.view`; a user who holds it at one property sees only that property). It rolls the immutable night-audit snapshots up over the last 7 / 14 / 30 / 90 days into occupancy, ADR, RevPAR and room revenue for the group and per property (with a daily occupancy bar strip), shows today live (arriving, leaving, in house), the next 14 days of bookings with the unguaranteed revenue at risk, Booking.com bookings secured by deposit and the deposit-conversion rate, no-show and late-cancellation fees recovered, cashier variance, open room issues, company receivables ageing, what is waiting for approval (bank transfers, cashier sessions, company payments, tax rates), and revenue by source and by company. Revenue figures exclude tax. Migration `0014` (one permission); run `pnpm --filter @hos/api roles:sync`. Not yet built: push alerts, complaints SLA beyond open room issues, and the three-property comparison as a chart.

**Slice 15 (OTA receivables):** when an OTA (not the guest) owes a no-show or late-cancellation fee, **Claim from OTA** on the booking's bill moves it off the guest's bill onto an OTA claim (idempotent; OTA bookings only). The claim is then marked sent to the OTA (with their reference), money received is recorded against it (partial payments allowed, each with a reference), it can be disputed and resolved, and what will never arrive is written off by a manager with a reason and the second factor. A claim not yet sent can be taken back (the amount returns to the guest's bill). Every step is kept in an append-only history; an **OTA claims** tab lists what is owed with ageing (0–30 / 31–60 / 61–90 / 90+ days), and the management overview shows what OTAs owe and what was written off. Amounts claimed from OTAs show in the night audit as their own line, never as revenue. Migration `0015`; run `pnpm --filter @hos/api roles:sync`. Not yet built: importing the OTA's payout statement to match payments automatically, and PayFast guarantee requests (waiting on PayFast's documentation and sandbox).

**Slice 16 (bulk import):** an **Import** tab brings in **guests** and **corporate accounts** from Excel. Paste the cells (or open a CSV); headings are recognised by name in any order (otherwise the columns are taken in the order shown), and a blank sheet can be downloaded. A check shows, row by row, what is new, already in the system, repeated in the file, or has a problem (missing name, invalid phone or email, unknown country, bad credit limit) without saving anything. Importing re-checks every row, adds only the new ones, is safe to retry, and is audited. Phone numbers that Excel stripped of their leading zero are recognised, and nationalities may be names ("Pakistan", "British") or codes. For guests already known (matched by phone or email) the choice is to skip them or fill in only their blank fields; companies that already exist are never changed. Importing companies with credit needs the second-factor code. Needs the `data.import` permission (owner, GM, property admin, accountant). Migration `0016`; run `pnpm --filter @hos/api roles:sync`. Not yet built: importing historical reservations, and rate cards.

**Slice 17 (maintenance work orders):** a **Repairs** tab turns a fault into a job with a number, a priority, a technician and a due date. A manager creates it (optionally from a housekeeping report) and can take the room out of order for the job in the same step, so the room cannot be sold meanwhile. The technician starts it, can park it waiting for parts, and finishes it with a note, cost and who supplied or did it; **someone other than the person who did the work checks it** (the same rule applies to owners), which puts the room back on sale, marks it dirty for housekeeping and closes the housekeeping report. A job that does not pass is sent back; a cancelled job releases the block. Technicians see only their own jobs; every step is on an unchangeable history. New role **Maintenance Technician**; the management overview shows open, overdue and to-check repairs per property. Migration `0017`; run `pnpm --filter @hos/api roles:sync`. Not yet built: recurring preventive maintenance, spare-parts stock, and attaching photos.

**Slice 18 (compliance rules):** a **Compliance** tab where managers write rules, not code. A rule matches a booking and/or a check-in by nationality (or everyone except some), residency, property, party size and length of stay, within optional dates, and then does one of: **note** or **warn** (shown to staff, in Urdu where the rule has Urdu wording), **require a manager's approval** (reason + second factor, carried over from booking to check-in), **create a task** (e.g. arrange security; listed on the Compliance tab, with who did it), **require a document** (the main guest must be registered with one of the listed ID types), or **block** the booking. Rules start as drafts and apply once turned on; every edit is audited with before and after. Every match is recorded against the booking (once per rule and stage) with who approved it and why, and shown on the reservation; walk-ins go through the same rules. The product ships with **no rules**: what applies to which nationality in which city is for the property's legal and security advisers to decide. Migration `0018`; run `pnpm --filter @hos/api roles:sync`. Not yet built: the quote-stage check on the new-booking screen before choosing a room, police/FIA report formats, and rule versions beyond the audit trail.

**Slice 19 (payment accounts):** every non-cash receipt now says which account it went into. An **Accounts** tab keeps the registry (bank accounts, card machines, wallets, gateways) with the bank, the last four digits and **who owns the account**: the company, a person, or someone else — an account that is not the company's must say whose and is shown in red everywhere. Once accounts of the right kind exist, recording a bank transfer, card slip, wallet payment, bank refund, company payment or OTA payout requires choosing one (never guessed; cash goes to the cashier's drawer). The accounts report shows, for any period, what was received into and paid out of each account, the total received into accounts that are not the company's, and receipts taken before any account was named, so nothing is invisible; the management overview shows the same. Setting up accounts needs the second factor. Migration `0019`; run `pnpm --filter @hos/api roles:sync`. Not yet built: bank-statement import and matching, and card/wallet settlement reconciliation.

**Slice 20 (kitchen and room service):** a **Kitchen** tab. Each property has a menu (section, name, Urdu name, price; items can be switched off, and an order already taken keeps the price it was taken at). Anyone with order rights takes an order for a guest who is in the house; the kitchen sees a queue (oldest first, with minutes waiting) and marks orders cooking and ready; whoever hands the food over marks it delivered, and **only then** is the guest's bill charged, item by item (so the tax engine and the invoice show real lines), once, even on a retry. Complimentary items post nothing. An order can be cancelled until it is delivered; after that the charges are reversed on the bill like any other. Orders for a guest whose bill is closed are refused. Migration `0020`; run `pnpm --filter @hos/api roles:sync`. Not yet built: restaurant tables and walk-in covers paid at the counter, stock and recipe costing, and a printed kitchen ticket.

**Slice 21 (staff, accounts and the audit trail):** the people side of the system now works from the app, not only from the command line. **Staff** tab: add a person (a one-time sign-up link, valid 7 days, shown once, which can be sent on WhatsApp), give and remove roles per property or for the whole business, issue a new link (a password reset for someone already active), disable or re-enable an account (which signs the person out everywhere), and reset a lost second factor. The rules keep the business safe: a role can only be made of permissions the person giving it holds, at places and limits within their own; a manager cannot touch an account that holds more authority than theirs (a property manager cannot disable the owner); nobody can change their own roles or disable themselves; the business always keeps one active owner; every step needs a reason where it matters and is audited. People open their link to **choose a password**, and **My account** (name in the header) lets anyone change their password and set up the second factor with an authenticator app, showing recovery codes once. An **Audit trail** tab (needs the second factor) shows who did what, newest first, with filters. Needs no migration. Not yet built: password-policy settings per business, session list and remote sign-out for the user themself, and e-mail delivery of links (they are handed over by hand or WhatsApp).

**Slice 22 (report downloads):** a **Reports** tab with spreadsheet downloads (CSV, opens in Excel) for any period up to 400 days: daily summary (occupancy, ADR, RevPAR, revenue, tax, movement), revenue by code / room type / source, the payments register (method, reference, account and its owner, who recorded it), the invoice register, tax collected, open bills and the in-house list; and, across the business, company receivables ageing and the payment-accounts report (accounts that are not the company's are marked). Same permissions as seeing the figures on screen. Cells are safe to open: anything that starts like a formula (a guest named `=HYPERLINK(…)`) is defused, Urdu names open correctly, amounts are plain decimals and dates are `YYYY-MM-DD`. Needs no migration. Not yet built: scheduled e-mailed reports, PDF layouts, and a general report builder.

**Slice 23 (conference room):** a **Conference room** tab. A *space* (the Boulevard conference room) has an hourly price, a half-day price (up to 4 hours), a full-day price (up to 12 hours) — any of them can be left out — and a changeover time kept free after each hire. The calendar cannot be double-booked: the database itself refuses two hires that overlap (the changeover counts as taken), and a cancelled hire frees the slot. Each hire is charged one of two ways: **to a staying guest** (a charge on that stay's bill, so it is taxed, invoiced and settled with the room), or on **a bill of its own** for someone not staying with us (a company can be noted on it); the own bill takes deposits and payments straight away (`POST /folios/:id/payments`, the same cash / card slip / wallet / bank-transfer rules as a stay) and cancelling is refused once money is on it. The charge goes on the bill when the hire is marked done, once, even on a retry; its tax code is `HALL`, so add it to the tax rules like any other code (nothing is taxed until you do). Amounts are before tax. Migration `0021`; run `pnpm --filter @hos/api roles:sync` (new permissions `space.view`, `space.book`, `space.manage`). A hire that has not happened yet can be changed (time, price type, details): the price is worked out again and the slot checked again (`PATCH /spaces/bookings/:id`, with the version). Not yet built: a cancellation fee and recurring bookings.

**Slice 24 (invoices and company billing for conference-room hires):** a hire on its own bill can now be given a numbered **tax invoice** (`POST /spaces/bookings/:id/invoices`; same gapless numbering, tax lines from the posted charge, credit notes and print page as a stay's invoice; it names the host, or a company with its NTN/STRN, and the hire's space, date and time) and can be **billed to a company on credit** (`POST /spaces/bookings/:id/bill-to-company`, Idempotency-Key; credit limit, hold and manager-override rules exactly as for a stay). Both need the hire to be marked done first. The invoice code was split so a stay and a hire share one implementation, and a company's receivable now lists the invoices on its bill whether it came from a stay or a hire. A hire charged to a staying guest is still invoiced and billed through the stay. Needs no migration. Not yet built: invoicing several hires on one invoice.

**Slice 25 (navigation and a browser test of the back office):** the owner and managers have more than twenty tabs, so they are now grouped into **Front desk, Housekeeping, Money and Management**: a sectioned side menu on a PC, and on a phone a section picker in the header with only that section's tabs in the bottom bar (it remembers the last tab used in each section). Staff whose work is one kind (a housekeeper, a cook) still see a plain list. The desktop header no longer overlaps the side menu. A new browser test, `apps/staff-web/e2e/office.mjs`, opens every tab as the owner and walks the conference room and kitchen menu through a real browser; the two older browser tests were re-run against the current build and pass. Needs no migration.

**Slice 26 (changing a conference-room hire, and the real rate card):** a booked hire can be changed from the screen (**Change**): time, price type, event and host; the price is worked out again and the slot checked again. The seeds now carry the owner's rate card and each property's real room types (Creek sells Standard, Executive, Deluxe Triple and Family Suite). The header on a PC no longer repeats the property name when there is a property picker.

**Slice 27 (setup check):** a **Setup check** tab (Management section; anyone with the management view, for the properties they may see) that reads the live configuration and says, per business and per property, what **needs doing** (tax area and an approved tax rate in force, the company's NTN and STRN, a nightly price for every room type, a payment account), what is **worth a look** (staff without a second factor, extra-person prices of zero, no separate weekend price and which days count as weekend, an empty kitchen menu, no conference room, room types with no rooms) and what is fine. It changes nothing and assumes nothing; its job is that no money runs on a guess. `GET /v1/readiness`. Needs no migration.

**Slice 28 (real room layout):** the seed now builds each property's rooms exactly as the owner described them: the room types each sells, how many of each are on the basement, ground floor and floor 1 (Ramna has a basement; Creek's Family Suite and Deluxe Triple are on two floors), so the housekeeping board, rack and reports group rooms by their real floors. Needs no migration; run `bash scripts/reset-dev.sh` to rebuild your local database with it.

**Slice 29 (the tax matrix, digital food, third-party transport reviews):** the owner's tax matrix is now in the system as **configuration, not code**. `seed:sunset-tax` (run by `reset-dev.sh`) enters it as **drafts** authored by the accountant (`accountant@sunset.local`) and points each property at its tax area (Boulevard and Creek → `SRB`, Ramna → `FBR-ICT`); nothing is charged until a *different* person (the owner, with the second factor) approves each rate in **Tax** with the advisor's reference and legal basis, as for every rate. The effective date in the drafts (2026-01-01) is a placeholder: edit it before approving. The matrix as entered: **Islamabad (FBR)** 15% on rooms, cash food, conference room, own and third-party transport and laundry, **5%** on food paid digitally; **Karachi (SRB)** 15% on rooms, cash food and the conference room, **8%** on food paid digitally and on transport, laundry exempt. To express it the charge codes are now `FNB` (food, cash) and `FNB_DIGITAL`, and `TRANSPORT_OWNED` and `TRANSPORT_THIRDPARTY` instead of `TRANSPORT`. A kitchen order says up front whether the guest **will pay digitally**, and is charged and taxed accordingly; staff pick the matching code for manual charges. **Charge reviews:** a rule per tax area says a charge code needs a person to look at it; posting such a charge opens a review (Islamabad: *withholding-tax review* of third-party transport; Karachi: *vendor verification*), shown at the top of **Compliance** and closed with a note that stays on record. Migration `0022` (also adds the `pay_digital` flag to kitchen orders); run `pnpm --filter @hos/api roles:sync`. **To confirm with the owner:** extra bed/person is taxed as accommodation (it is not in the matrix); minibar, miscellaneous, cancellation and no-show fees are untaxed because the matrix does not list them; whether the digital rate must be re-checked if a guest says digital and then pays cash. Not yet built: a screen to edit the review rules, and checking the way a bill is finally paid against the digital/cash choice made when the food was ordered.

**Slice 30 (Rates screen, real room numbers and extras):** a **Rates** tab (Money section; for whoever manages rates) so prices are changed on screen, not by a developer: per room type the nightly price, an optional weekend price (blank = same as weekday), the extra-adult and extra-child price and how many adults and people it sleeps; the extra-mattress price for the plan; which days count as the weekend; and, for the international plan, the percentage above (or below) the local price. Saving is audited like any rate change. The seed now carries the real room numbers and floors, the extra-person and extra-mattress prices, and an international plan equal to the local price. The *weekend price not set* line is gone from the Setup check, since one price all week is the owner's decision. Needs no migration; run `bash scripts/reset-dev.sh` to rebuild.

**Slice 31 (rooms screen):** a **Rooms** tab (Management section; whoever manages the property) listing rooms by floor with their type, where a room's **number, type, floor, notes, accessible/smoking flags** can be corrected and a room **retired** (not while guests are assigned or blocks are open), and a new room **added**. Renumbering is new in the API (`PATCH /rooms/:id` accepts `number`; numbers stay unique per property; audited); past bills and invoices keep the number they were made with. This is how the Ramna numbers are corrected without a developer. Needs no migration.

**Slice 33 (bank accounts and the cash safe):** the owner's accounts are recorded (`seed:sunset-accounts`, run by `reset-dev.sh`; in real use entered on **Accounts**): three bank accounts in **Farooq Saleh's personal name**, one per property (Faysal Bank for Creek, Bank Alfalah for Boulevard, Bank Al Habib for Ramna), described by the owner as for non-tax personal transfers, and one **company** account (Bank Al Habib, Sunset BNB) for taxable invoices and company transfers. A bank transfer must say which account it went into; accounts not owned by the company are flagged in every report and the Accounts summary. **The system does not have a way to leave a payment, or its tax, out of the books**: tax is charged on the bill's charges whichever account the money lands in, and every receipt is recorded against its account. **Cash** is not an account: each register is counted blind and closed daily (that is the day's *envelope*); envelopes accumulate in the property's **safe**, shown on the **Cashier** screen to managers (`cashier.review`) with the envelopes by day and register; once a week the cash is handed to head office and the **handover** is recorded (amount, who received it, their role, the safe balance at that moment, and a reason if it is less than the whole safe), with a fresh second factor (`cashier.handover`, new permission: run `pnpm --filter @hos/api roles:sync`). Handovers are immutable; a mistake is corrected by a later, explained entry. Migration `0023`. Not yet built: what head office does with the cash afterwards (drawings, payments) and a printed handover receipt.

## Run it on your Mac (no cloud needed)
Requires Node 22+, pnpm 10 (`corepack enable`), and Docker Desktop (or a local PostgreSQL 16). `psql` need not be installed: the scripts fall back to the one inside the database container.
```bash
pnpm install
pnpm build                                                                     # builds the shared packages (@hos/db, @hos/auth, …) the apps import
docker compose up -d db                                                        # PostgreSQL 16 on localhost:5432
PGSUPERUSER_URL=postgres://postgres:postgres@localhost:5432/postgres bash scripts/bootstrap-db.sh
cp .env.example .env                                                           # then put a real key in APP_ENCRYPTION_KEY (command in the file)
bash scripts/reset-dev.sh                                                      # applies migrations, seeds Sunset + demo staff (safe to re-run: it wipes dev data)
pnpm --filter @hos/api dev                                                     # API on http://localhost:3000 (terminal 1)
pnpm --filter @hos/staff-web dev                                               # staff app on http://localhost:3001 (terminal 2)
```

## Rules that are enforced in code review and CI
1. Every tenant-owned table has `tenant_id`, forced RLS and a policy; the lint in `packages/db/test/schema-lint.test.ts` fails otherwise.
2. Tenant data is accessed only through `TenantDb.tx()` / `withTenant()`; the tenant comes from the authenticated principal, never from client input.
3. Money is `Money` (integer minor units). Never `number` for amounts.
4. Ledgers (`audit_log`, future `folio_posting`) are append-only: no UPDATE/DELETE.
5. No secrets in the repository; production credentials come from AWS Secrets Manager.
